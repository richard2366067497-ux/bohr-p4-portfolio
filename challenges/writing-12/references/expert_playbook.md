# 专家参考手册 · LaTeX 写作、编译与核验（writing-12）

> 本手册是本 Skill 的核心方法论基准：执行前必读。任务本质、错误做法→正确做法、求解框架、
> 量化口径、领域知识、交付物检查表与案例均以本手册为准；与 `SKILL.md` 冲突时，契约键名与
> 入口命令以 `SKILL.md` 为准，方法与判分口径以本手册为准。

---

## 1. 任务本质与判分要点

### 1.1 任务本质

交付物是**可编辑、可编译、可复核的 `.tex` 源码及配套资源**，而不是一张 PDF 或截图。PDF 只
作为渲染预览；真正被评估的是源码、编译日志、来源映射、变更记录与可复现说明。评测会在未知
案例上读取实际材料并真实运行，任何依赖文件名或领域标签的猜测都不算证据。

一份合格的交付包含三面：

1. **源码面**：符合模板约束的完整 `.tex`（及 `.bib`、子文件、本地 `.cls/.sty`）。
2. **证据面**：每个数字、术语、引用、图表都能回溯到材料中的具体定位。
3. **边界面**：修改差异、人工确认项、材料缺口、异常情形显式标注，未验证的构建如实记为未验证。

### 1.2 判分要点（优先级从高到低）

1. **实际效果**：能否编译通过；公式、表格、引用是否正确；任务要求是否被覆盖完整、可核验。
2. **使用增益**：相对基础 Agent，编译成功率与修复正确率是否提升；是否有同条件公平对照。
3. **创新增益**：错误分类、可逆修复策略、编译验证闭环等是否形成可运行能力，而非填空模板。
4. **可靠体验**：跨模板、跨 TeX 发行版是否稳定；对缺引擎、缺宏包、缺字体等异常能否识别处置。
5. **生态贡献**：文档、脚本、模板、检查清单是否可独立复用、可分享。

### 1.3 错误做法 → 正确做法

| 错误做法 | 正确做法 |
|---|---|
| 把 PDF/截图当最终结果 | 交付可编辑 `.tex` 源码，PDF 仅作预览 |
| 只修第一条编译错误 | 定位到文件:行号:根因，识别错误级联并逐层处理 |
| 忽略模板必填项 | 逐项核对 `\author`、`\title`、`\affiliation`、`abstract`、`\keywords` 等 |
| 不保留来源 | 每个数字/术语/引用/图表都给 `文件:行号` + 逐字引用 |
| 虚构数据或软件状态 | 材料缺失时标“材料未提供，需人工确认”，不补造 |
| 不读实际材料 | 解析实际输入文件，不能据文件名或标签假设内容 |
| 不写 `result.json` | 每次运行都返回结构化结果，逐键回填 `output_contract` |
| 超预算丢中间产物 | 每步把中间产物落到 `--work`，最终结果写入 `--output` |
| 用领域标签补数据 | 事实只能来自输入材料与原论文，不据标签推断 |
| 忽略宏包/字体缺失 | 识别缺宏包、缺字体、缺类文件，并给出安装或替代方案 |
| 擅自改动科学语义 | 仅做可逆、可解释的修复；语义改动一律标为需人工确认 |

## 2. 求解框架（7 步）

正式产物写入 `--output`，中间产物写入 `--work`。下表“冻结产物”一旦通过门控，后续修改必须留痕。

| 步骤 | 操作 | 冻结产物 | 门控条件 |
|---|---|---|---|
| S0 环境与输入 | 读 `case.json`、`task.md` 与实际材料；记录文件哈希 | 输入清单（路径、类型、哈希、可读性） | 必需文件存在且可读；解析失败单独记录不中止 |
| S1 任务解析 | 识别任务类型：生成/改写/校对/结构化/模板迁移/编译修复；提取体裁、受众、格式、必填项 | `task_class.json` | 任务类型明确；必填项清单非空；模糊处记不确定性 |
| S2 事实提取 | 从材料抽取数字、术语、引用、图表、关键论断 | `facts.jsonl`（`fact_id/content/source_locator/confidence`） | 每条事实有 locator 或标记缺口 |
| S3 源码生成/修改 | 依模板生成或修改 `.tex`，严格使用事实 | `main.tex`、`refs.bib`、必要子文件 | 结构完整；模板必填项已填；事实与源码对应 |
| S4 静态检查 | 查宏包顺序、环境配对、公式语法、表格结构、引用键存在性 | `static_report.txt` | 无致命语法错误；警告可控 |
| S5 编译循环 | 运行 `latexmk -pdf -interaction=nonstopmode -halt-on-error`，解析日志定位根因并修复后重编 | `build.log`、`main.pdf`、`fix_log.txt` | 编译退出码 0；每处修复可定位 |
| S6 来源核对 | 逐条核对事实与源码，生成来源映射 | `source_map.json`、`diff.tex` | 事实可核验率 100%（含已标注缺口） |
| S7 交付 | 打包源码、映射、差异、日志与 `result.json` | `result.json` + 全部交付物 | 契约字段齐全；`case_id` 一致；文件可独立复核 |

**诚实规则**：没有 TeX 引擎或演示环境缺编译器时，`status=partial`，不得把“未编译”写成“编译通过”；
给出可执行的复现命令（如 `latexmk -pdf`）供他人复核。编译成功与“源码能编译”是同一回事，
必须有真实日志支撑。

## 3. 量化口径与公式

设成功编译案例数为 \(N_{\mathrm{success}}\)，总案例数为 \(N_{\mathrm{total}}\)；正确修复点数为
\(N_{\mathrm{correct\_fix}}\)，总修复点为 \(N_{\mathrm{fix}}\)。

\[
\mathrm{CSR}=\frac{N_{\mathrm{success}}}{N_{\mathrm{total}}}\times100\%,\qquad
\mathrm{FRR}=\frac{N_{\mathrm{correct\_fix}}}{N_{\mathrm{fix}}}\times100\%.
\]

| 指标 | 定义 | 公式 | 目标 |
|---|---|---|---|
| 编译成功率 CSR | 成功编译案例占比 | \(N_{\mathrm{success}}/N_{\mathrm{total}}\) | ≥90% |
| 修复正确率 FRR | 正确修复点占比 | \(N_{\mathrm{correct\_fix}}/N_{\mathrm{fix}}\) | ≥90% |
| 事实一致率 FCR | 源码事实与材料一致占比 | \(N_{\mathrm{consistent}}/N_{\mathrm{facts}}\) | 100% |
| 事实可核验率 FVR | (有来源+已标注缺口)/总事实 | \((N_{\mathrm{sourced}}+N_{\mathrm{gap}})/N_{\mathrm{facts}}\) | 100% |
| 编译轮次 \(N_{\mathrm{rounds}}\) | 首次编译到成功编译的次数 | 计数 | ≤3 |
| 警告降幅 WRR | (初始警告−最终警告)/初始警告 | \((W_0-W_1)/W_0\) | ≥50% 或最终≤5 |
| 效率增益 EG | (基础耗时−本 Skill 耗时)/基础耗时 | \((T_0-T_1)/T_0\) | ≥20%（须有实测对照） |

**计算示例**：某案例初始 3 个错误、8 个警告；修复后编译成功、剩 2 个警告；事实点 12 个，11 个有
来源、1 个标注“材料未提供，需人工确认”。则 CSR=1/1=100%，FRR=3/3=100%，FCR=12/12=100%，
FVR=(11+1)/12=100%，轮次=3，WRR=(8−2)/8=75%。

**增益口径**：没有同输入、同环境的真实对照，就写“未测”，不得自报提升百分比。

## 4. 领域知识清单

### 4.1 常见事实性错误

1. **宏包顺序**：`hyperref` 应在多数宏包之后加载，`cleveref` 在 `hyperref` 之后，否则链接/交叉引用失效。
2. **正斜体**：变量斜体（`$x$`），单位正体（`\si{\meter}`），函数名正体（`\sin`、`\log`）。
3. **表格溢出**：宽表用 `tabularx`/`longtable`/`adjustbox`，不靠缩小字号硬塞。
4. **引用未定义**：`\cite`/`\ref` 需多遍编译，且 `.bib` 条目存在、键名一致。
5. **模板必填项**：期刊模板的 `\thanks`、`\affiliation`、`\keywords`、`\begin{abstract}` 等漏填会直接影响评审。
6. **浮动体位置**：图表用 `[htbp]` 或 `[!t]`，避免错位漂移。
7. **三线表**：用 `booktabs` 的 `\toprule/\midrule/\bottomrule`，不加竖线。
8. **文献样式**：按模板要求设 `\bibliographystyle`，排序与引用风格一致。
9. **错误级联**：只修第一条会反复重编；应按最早可指认的根因修复。
10. **环境不可复现**：记录 TeX 发行版与关键宏包版本，否则他人无法复现。

### 4.2 单位/量纲陷阱

- 用 `siunitx`：`\SI{25.7}{\percent}`、`\SI{10}{\meter}`，数值与单位之间留空格，不用 `10m`。
- 量纲一致：如 \(\eta=P_{\mathrm{out}}/P_{\mathrm{in}}\) 无量纲；功率、能量、时间单位须自洽。
- 有效数字一致：表格内 `25.7` 与 `25.70` 不可混排。
- 温度 ℃ 与 K、mbar 与 Pa、mL 与 μL 的换算须显式写出，不静默转换。

### 4.3 文献依据要求

- 每个 `\cite` 必须有对应 `.bib` 条目，且正文键与条目键逐字一致。
- 引用格式遵循模板（IEEE/APA/ACS 等）；不得为排版顺畅补造引用。
- 不得新增材料外事实；确需补充时标“假设/需人工确认”。
- 来源 locator 精确到 `文件:行号` + 逐字引用；PDF 材料给页/节/表图定位。

## 5. 交付物清单与专家检查表

### 5.1 必需交付物

| 文件 | 内容 | 自证方式 |
|---|---|---|
| `main.tex` | 可编辑、可编译的根源码（修复已应用，输入原文件不改写） | 打开即可编辑；有引擎则独立编译 |
| `source/` | 工程树（子文件、`.bib`、本地类/样式、图片） | 相对路径完整，可整体复制编译 |
| `refs.bib` | 参考文献条目，与正文对应 | 键名逐一核对 |
| `main.pdf` | 编译成功时的合法 PDF（头 `%PDF-`） | 打开可读；与源码一致 |
| `diff.patch` / `diff.tex` | 输入→输出的统一差异 | 逐行可核验改动 |
| `source_map.json` | 事实→`fact_id/source_locator/content` 映射 | 抽查任一数字可回到原文 |
| `build.log` / `lint_report.json` / `fixes.json` | 编译与静态检查、修复记录（含 before/after/locator） | 日志可复算 |
| `packages.md` | 所需宏包、编译命令、引擎选择 | 命令可执行 |
| `result.json` | 逐键回填 `output_contract` + `case_id` + 状态 | `python -m json.tool` |

### 5.2 专家检查表（逐项通过方可交付）

- [ ] 已读 `case.json`、`task.md` 与实际材料，而非据文件名假设。
- [ ] 已识别任务类型与全部格式/必填项约束。
- [ ] 已提取全部事实点，每条有 locator 或缺口标注。
- [ ] 模板必填项齐全（作者、标题、单位、摘要、关键词等）。
- [ ] 宏包加载顺序正确（`hyperref` 后置）。
- [ ] 公式正斜体、单位正体、函数名正体处理正确。
- [ ] 表格无溢出，三线表样式正确。
- [ ] `\cite`/`\ref` 多遍编译后无未定义，`.bib` 条目齐全。
- [ ] 编译错误定位到文件:行号:根因，已处理级联而非只修第一条。
- [ ] 记录了编译轮次、警告数、错误数。
- [ ] `result.json` 逐键回填、`case_id` 与原值一致、无类型占位符。
- [ ] 中间产物在 `--work`，最终结果在 `--output`。
- [ ] 材料不足、冲突、需人工确认项已明确标注。
- [ ] 给出了可执行复现命令（如 `latexmk -pdf -interaction=nonstopmode`）。
- [ ] 未虚构数据、软件状态或编译结果；缺引擎时如实记 partial。
- [ ] 可编辑产物与预览文件内容一致。
- [ ] 初稿/中间结果已提前落盘，后续为增量改进。
- [ ] 示例明确标为虚构演示，不含正式案例答案。

## 6. 完整虚构案例

> 以下材料、数据与输出均为演示虚构，不对应任何正式测试案例。

**输入**：`case.json` 声明 `case_id="CASE-2024-001"`，任务为“把一段钙钛矿太阳能电池稿件迁入
IEEE 模板并修复编译错误”。材料含公式 \(\eta=P_{\mathrm{out}}/P_{\mathrm{in}}\)、效率表
25.7%、引用 `[1]`，原稿有 3 个编译错误、8 个警告。

**关键中间量**：

| 步骤 | 产物 | 数值 |
|---|---|---|
| 事实提取 | `facts.jsonl` | 12 个事实点 |
| 静态检查 | `static_report.txt` | 3 错误、8 警告 |
| 编译循环 | `build.log` | 第 1 轮 3 错误 → 第 2 轮 1 错误 → 第 3 轮 0 错误、2 警告 |
| 来源映射 | `source_map.json` | 11 有来源，1 标“材料未提供，需人工确认” |
| 结果 | `result.json` | CSR=100%，FRR=100%，FVR=100%，轮次 3，WRR=75% |

**输出片段**：

```latex
\begin{equation}
  \eta = \frac{P_{\text{out}}}{P_{\text{in}}}
\end{equation}
```

```json
{
  "case_id": "CASE-2024-001",
  "status": "success",
  "output_contract": {
    "case_id": "CASE-2024-001",
    "status": "success",
    "deliverable": {"path": "main.tex", "role": "manuscript", "editable": true,
                    "compiled": true, "pdf": "main.pdf", "diff": "diff.patch", "source_tree": "source/"},
    "preserved_facts": [{"fact": "25.7% efficiency", "source": "manuscript.pdf:table2"}],
    "evidence_map": [{"segment": "efficiency 25.7%", "source": "manuscript.pdf:table2"}],
    "change_log": [{"step": "build", "action": "fix", "detail": "close missing \\end{document}"}]
  }
}
```

数字自洽：12 个事实点，11 有来源 + 1 标注缺口，FVR=(11+1)/12=100%；编译 3 轮成功，警告从 8 降到 2，
WRR=(8−2)/8=75%。**若本机无 TeX 引擎**，同一运行的 honest 结果应为 `status=partial`，
`build.status=missing_tool`，并附可执行编译命令——这是“未验证”，不是“通过”。

## 7. 交付前门控

- 逐项勾选 §5.2 检查表；任一未通过先修复再交付。
- `result.json` 可解析，`case_id` 与输入一致，`output_contract` 逐键回填且无类型占位符。
- 有引擎时 `main.pdf` 以 `%PDF-` 开头；无引擎时 `status=partial` 且给出可执行编译命令。
- `fixes[]` 每条有 `before/after/locator/applied`；`diff.patch` 可逐行核验。
- 所有异常分类记录（材料缺口 / 无法判断 / 构建未验证），不得伪装成“已完成”。
